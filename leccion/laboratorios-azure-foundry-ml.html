Laboratorio Azure: Foundry seguro y despliegue blue/green en Azure ML

Crea un recurso de Microsoft Foundry (AIServices), despliega un modelo con el SKU adecuado y desactiva las claves para usar solo Entra ID. Después, en Azure Machine Learning, crea un cómputo que escala a cero, entrena con un job YAML, registra dos versiones del modelo y hace un despliegue blue/green con tráfico espejo, canario y corte completo. Es la práctica de AI-103 y AI-300.

▶ Abrir la lección interactiva (18 ejercicios)

Al terminar vas a poder

  • Crear un recurso Foundry y un despliegue de modelo con el SKU correcto
  • Desactivar la autenticación por clave y el acceso público
  • Crear un cómputo de Azure ML que escala a cero y lanzar un job
  • Desplegar dos versiones en un online endpoint y mover tráfico con espejo y canario
  • Borrar todo con el grupo de recursos
🏢 El caso

Una clínica quiere un asistente con un modelo de OpenAI que procese los datos dentro de la zona de datos de EE. UU. y sin claves compartidas en el código. Su equipo de riesgo, además, tiene un modelo de crédito en Azure ML y quiere cambiarlo por la versión 2 sin cortar el servicio ni arriesgar a todos los clientes a la vez.

En tu cuenta real

az extension add -n ml
az provider register --namespace Microsoft.MachineLearningServices
# rol para que la app use Foundry sin claves
az role assignment create --assignee <object-id-de-la-identidad> \
  --role "Cognitive Services OpenAI User" \
  --scope $(az cognitiveservices account show -n foundry-lab-clinica -g rg-lab-ia --query id -o tsv)
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import AzureOpenAI

token = get_bearer_token_provider(DefaultAzureCredential(), "https://cognitiveservices.azure.com/.default")
cliente = AzureOpenAI(azure_endpoint="https://foundry-lab-clinica.openai.azure.com/",
                      azure_ad_token_provider=token, api_version="2024-10-21")
r = cliente.chat.completions.create(model="chat", messages=[{"role": "user", "content": "Hola"}])
print(r.choices[0].message.content)
  • Con --public-network-access Disabled solo entras por un private endpoint; para probar desde tu computadora, deja el acceso público y restringe por IP.
  • Los despliegues tardan de 5 a 15 minutos. Revisa los logs con az ml online-deployment get-logs --name green --endpoint-name riesgo-credito.
  • Comprueba la cuota de la familia de VM (Standard_DSv2) en la región antes de desplegar.

Limpieza

🐞 Errores frecuentes
  • Dejar habilitadas las claves de API del recurso de Foundry: cualquiera que copie la clave tiene acceso. Desactivarlas obliga a usar identidades de Entra ID con permisos.
  • Asignar el rol a la persona y no a la identidad de la aplicación: funciona en la prueba y falla en producción.
  • Cómputo de entrenamiento con mínimo de nodos mayor que cero: cobra aunque no haya jobs.
  • Pasar el tráfico al despliegue verde de golpe: si falla, falla para todos. Se pasa de a poco y se compara.
  • Olvidar borrar el online endpoint: es de lo más caro del laboratorio.
🧑‍💻 En el trabajo real
  • En Azure, las empresas desactivan las claves locales de los servicios de IA y usan identidades administradas con roles mínimos, auditados con Entra ID.
  • El despliegue blue/green de modelos se automatiza en el pipeline de CI/CD: crear el despliegue nuevo, probarlo con tráfico espejado o parcial, y cambiar el tráfico.
🎯 "¿Por qué desactivarías las claves de un servicio de IA y usarías Entra ID?"

Porque una clave es un secreto compartido de larga duración que cualquiera que la tenga puede usar, y no identifica quién hizo cada llamada. Con Entra ID cada aplicación usa su propia identidad, idealmente una identidad administrada, con un rol que limita qué puede hacer; los tokens son de corta duración, los accesos quedan auditados y se pueden revocar sin cambiar el código de las demás aplicaciones.
