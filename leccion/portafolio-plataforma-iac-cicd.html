Proyecto 11: La plataforma con Terraform, Declarative Automation Bundles y CI/CD

Lo que convierte proyectos sueltos en una plataforma profesional. Toda la infraestructura en código con Terraform (grupo de recursos, lago, Key Vault, workspace de Databricks), los pipelines y jobs en un Databricks Asset Bundle con entornos dev y prod, y GitHub Actions que validan cada cambio y despliegan al aprobar. Usas cualquiera de los proyectos anteriores como carga de trabajo. Valor - desplegar en minutos, igual en cada entorno y sin pasos manuales.

▶ Abrir la lección interactiva (7 ejercicios)

Al terminar vas a poder

  • Describir infraestructura de Azure y Databricks con Terraform y estado remoto
  • Empaquetar jobs y pipelines en un Asset Bundle con targets dev y prod
  • Diseñar un flujo de CI que valide, pruebe y despliegue
  • Autenticar la CI sin secretos de larga duración (OIDC o identidades federadas)
  • Explicar cómo se promueve un cambio de dev a prod
🏢 El caso

El equipo tiene tres proyectos en producción, creados a mano desde la consola. Nadie sabe exactamente qué configuración tiene el job de producción, un cambio "rápido" rompió el pipeline del viernes y el entorno de pruebas no se parece al de producción. La líder técnica pide: "todo en código, revisado por pull request y desplegado igual en todos lados".

Qué va en cada herramienta

Capa Herramienta Ejemplos
Infraestructura de la nube Terraform (azurerm + databricks) Grupo de recursos, cuenta de almacenamiento, Key Vault, workspace, catálogos y permisos
Cargas de trabajo de datos Databricks Asset Bundle Jobs, pipelines declarativos, notebooks, tableros
Automatización GitHub Actions Lint, tests, terraform plan, bundle validate y deploy

Regla práctica: lo que cambia poco y crea recursos (la infraestructura) va en Terraform; lo que cambia todas las semanas con el código de datos va en el bundle, en el mismo repositorio que ese código.

Arquitectura

Fase 1: Terraform

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateacademia"
    container_name       = "tfstate"
    key                  = "plataforma.tfstate"
  }
}

resource "azurerm_resource_group" "rg" {
  name     = "rg-datos-${var.entorno}"
  location = "eastus2"
  tags     = { proyecto = "plataforma", entorno = var.entorno }
}

resource "azurerm_storage_account" "lago" {
  name                     = "stlago${var.entorno}${random_string.sufijo.result}"
  resource_group_name      = azurerm_resource_group.rg.name
  location                 = azurerm_resource_group.rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  is_hns_enabled           = true
}
  • Estado remoto con bloqueo: dos personas (o dos ejecuciones de CI) no pueden aplicar a la vez, y el estado no vive en la computadora de nadie.
  • Un estado por entorno (dev, prod), con variables distintas: mismo código, distinta escala.

Fase 2: el Asset Bundle

# databricks.yml
bundle:
  name: ventas_lakehouse

include:
  - resources/*.yml

targets:
  dev:
    mode: development        # prefija los recursos con tu usuario y pausa los horarios
    default: true
    workspace:
      host: https://adb-1111111111111111.1.azuredatabricks.net
  prod:
    mode: production
    workspace:
      host: https://adb-2222222222222222.2.azuredatabricks.net
    run_as:
      service_principal_name: sp-datos-prod   # producción no corre con un usuario personal
# resources/ventas.job.yml
resources:
  jobs:
    ventas_diarias:
      name: ventas_diarias
      schedule: { quartz_cron_expression: "0 0 6 * * ?", timezone_id: "America/Bogota" }
      tasks:
        - task_key: dbt_build
          dbt_task: { project_directory: ./transform, commands: ["dbt deps", "dbt build"] }

Fase 3: CI/CD con GitHub Actions

# .github/workflows/ci.yml
on:
  pull_request:
  push: { branches: [main] }
permissions: { id-token: write, contents: read }   # OIDC: sin secretos de larga duración
jobs:
  validar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv run ruff check . && uv run pytest
      - run: uv run dbt build --target ci          # contra DuckDB, rápido y gratis
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate -t dev
  desplegar_prod:
    needs: validar
    if: github.ref == 'refs/heads/main'
    environment: produccion                        # requiere aprobación manual
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle deploy -t prod

La autenticación de la CI usa identidades federadas (OIDC): GitHub presenta un token firmado y Azure o Databricks confían en él según el repositorio y la rama. No hay claves guardadas que puedan filtrarse.

🐞 Errores frecuentes
  • Un estado de Terraform local en un proyecto de equipo: se pierde o dos personas lo pisan. Usa un backend remoto con bloqueo.
  • Secretos en el repositorio o en variables sin marcar como secretas en el CI.
  • Desplegar a producción desde tu computadora.
  • Sin plan/what-if en el pull request: el revisor no ve qué va a cambiar en la nube.
🧑‍💻 En el trabajo real
  • Un proyecto que muestra infraestructura como código, entornos separados y despliegue automático con aprobación es justamente lo que piden los puestos de plataforma de datos y los semi senior.
🎯 "¿Cómo organizarías el despliegue de una plataforma de datos con varios entornos?"

Infraestructura en Terraform o Bicep con estado remoto y un archivo de variables por entorno; jobs y pipelines en bundles con targets dev y prod. Cada cambio por pull request, con CI que corre validaciones, tests y el plan o what-if publicado en el PR. Al aprobar, el CI despliega a prod con una identidad de servicio vía OIDC, con aprobación manual para producción, y nadie cambia producción a mano.

🖥️ En tu computadora y en la web real

Todo el proyecto se hace en tu computadora:

  1. Terminal: Terminal en macOS, o Ubuntu con WSL en Windows (wsl --install en PowerShell como administrador). Ahí corres git, uv y las CLIs.
  2. VS Code con las extensiones de Python, Jupyter y la del servicio que uses (Databricks, Azure).
  3. Una carpeta por proyecto con git init desde el primer minuto, y un repositorio público en github.com → New repository para mostrarlo.
  • Terraform en tu computadora: brew install terraform (o winget install Hashicorp.Terraform), terraform init, plan y apply contra tu cuenta.
  • Bundle: databricks bundle validate y databricks bundle deploy -t dev desde la terminal, después de databricks auth login.
  • GitHub Actions: el workflow corre en github.com; las credenciales van en Settings → Secrets and variables → Actions (o con OIDC, sin secretos).

Práctica

🛠️ Practícalo en la herramienta: Infraestructura y código, validados como en CI
  1. Terraform crea la base (un bucket por capa) y se valida como en un pipeline: fmt -check, validate, plan.
  2. El bundle de Databricks se valida y despliega al entorno de desarrollo.
  3. Esos mismos comandos son los pasos del workflow de GitHub Actions.
aws configure
mkdir -p ~/plataforma && cd ~/plataforma
printf 'resource "aws_s3_bucket" "bronze" {\n  bucket = "plataforma-dev-bronze"\n}\n' > main.tf
terraform init
terraform fmt -check
terraform validate
terraform plan
databricks auth login --host https://adb-1234567890123456.7.azuredatabricks.net
databricks bundle init
cd mi_proyecto
databricks bundle validate
databricks bundle deploy -t dev
🔍 Qué hace cada comando (12)
  1. aws configureaws: la CLI de AWS: hace desde la terminal lo mismo que la consola de AWS. configure guarda tus credenciales y la región por defecto
  2. mkdir -p ~/plataforma && cd ~/plataformamkdir: crea una carpeta. -p = crea también las carpetas intermedias y no falla si ya existe → si sale bien, sigue el próximo
    cd: entra a una carpeta (cambia el directorio de trabajo). cd .. sube un nivel y cd ~ vuelve a tu carpeta personal
  3. printf 'resource "aws_s3_bucket" "bronze" {\n bucket = "plataforma-dev-bronze"\n}\n' > main.tfprintf: escribe texto con formato (como echo, pero controlando saltos de línea y columnas). > guarda la salida en un archivo (lo reemplaza si existe)
  4. terraform initterraform: Terraform: crea y cambia infraestructura en la nube a partir de archivos .tf. init prepara la carpeta: descarga los proveedores y configura dónde se guarda el estado
  5. terraform fmt -checkterraform: Terraform: crea y cambia infraestructura en la nube a partir de archivos .tf. fmt ordena el formato de los archivos .tf
  6. terraform validateterraform: Terraform: crea y cambia infraestructura en la nube a partir de archivos .tf. validate revisa que la configuración sea válida
  7. terraform planterraform: Terraform: crea y cambia infraestructura en la nube a partir de archivos .tf. plan muestra qué va a crear, cambiar o borrar, sin hacerlo
  8. databricks auth login --host https://adb-1234567890123456.7.azuredatabricks.netdatabricks: la CLI de Databricks: maneja el espacio de trabajo desde la terminal. auth inicia sesión y guarda el perfil del espacio de trabajo (login)
  9. databricks bundle initdatabricks: la CLI de Databricks: maneja el espacio de trabajo desde la terminal. bundle Declarative Automation Bundles: despliega jobs y pipelines como código (init)
  10. cd mi_proyectocd: entra a una carpeta (cambia el directorio de trabajo). cd .. sube un nivel y cd ~ vuelve a tu carpeta personal
  11. databricks bundle validatedatabricks: la CLI de Databricks: maneja el espacio de trabajo desde la terminal. bundle Declarative Automation Bundles: despliega jobs y pipelines como código (validate)
  12. databricks bundle deploy -t devdatabricks: la CLI de Databricks: maneja el espacio de trabajo desde la terminal. bundle Declarative Automation Bundles: despliega jobs y pipelines como código (deploy)

Se escribe en la terminal: la del curso (botón ⌨ Terminal) o la de tu computadora — Terminal en macOS, Ubuntu (WSL) o Git Bash en Windows. Escribe una línea y presiona Enter.

Reto: escribe el workflow .github/workflows/ci.yml con estos pasos y la condición para desplegar a prod solo desde main.
